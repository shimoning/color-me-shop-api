# 受注作成 API の実測記録

## この文書の位置づけと収集条件

この文書は、受注作成 API（`POST /v1/sales`）をライブラリに実装する判断のため、実 API の挙動を
記録する。現在のライブラリ仕様ではない。実測の出典はこの文書を追加・更新した各コミットであり、
[ADR 0000](adr/0000-record-architecture-decisions.md) の収集条件・検証可能性の規則に従う。

収集日は **2026-10-01（Asia/Tokyo）**。対象はテスト用ショップ。本ライブラリの `Communicator\Request`
で JSON の body を送った。

**受注は作成していない。** 必須項目を欠いた body だけを送り、実行後に受注の一覧を取得して、受注が
増えていないことを確かめた。アクセストークンは記録しない。

## 背景

公式 OpenAPI の `POST /v1/sales`（`operationId: createSale`）について、次の 3 点が実装前に分からな
かった。

- 説明文に「カラーミーショップでご契約中のプランがプレミアムのアカウントでのみご利用いただけます」
  とある。テスト用ショップで使えるかは分からなかった
- 操作に `security` キーがなく、グローバルの `security` もないため、OpenAPI の意味論では認証不要という
  宣言になる。一方、説明文には「write_salesスコープが必要です」とある。
  [OAuth スコープと公式 OpenAPI の突合記録](auth-scope-audit.md)は、記載漏れと考えたうえで「実装する際に
  実 API で確認する必要がある」と保留していた
- 成功時の応答（`201`）の形は公式 OpenAPI にしか根拠がない

## 観測

| | 条件 | HTTP | `code` | `message` |
| --- | --- | ---: | ---: | --- |
| A | 認証あり、body `{"sale": {}}` | 401 | 401200 | 現在契約中のプランではご利用いただけません。 |
| B | 認証あり、body `{"sale": {"payment_id": 0, "details": []}}` | 401 | 401200 | 同上 |
| C | 認証なし、body `{"sale": {}}` | 401 | 401010 | このリソースにアクセスできません。有効なアクセストークンが見つからないか、必要なスコープが付与されていません。 |

応答の形はいずれも、API 本体の `{"errors": [{"code", "message", "status"}]}` 形式だった。

**テスト用ショップの契約プランでは、受注作成は使えない。** プランの判定は body の検証より先に行われる。
中身の異なる A と B が同じ応答になったため、必須項目の検証（422）までは到達していない。

**受注作成には認証が必要である**（ケース C）。公式 OpenAPI に `security` がないのは記載漏れと判断できる。

## 確かめていないこと

- **成功時の応答の形。** プランの制約により受注を作成できず、`201` を観測していない。公式 OpenAPI の
  `201` の `sale` は、受注の取得（`GET /v1/sales/{sale_id}`）と同じ 44 項目である
- **`write_sales` スコープが必要か。** 実測に使ったトークンは受注の更新に使えており、`write_sales` を
  持っている。スコープを持たないトークンとの比較はしていない。ケース C のメッセージはスコープにも
  触れているが、トークンなしの応答であり、スコープの要否は判別できない
- 必須項目の検証（`422`）の内容、`reserve_stocks` の効果、既存顧客の `customer.id` を指定したときに
  他の顧客情報が無視されること、`price` の指定
- 観測は 1 ショップで、各ケース 1 回ずつである

利用できる契約プランのショップで、作成の成功と上記を実測できた時点で、この文書を更新する。
