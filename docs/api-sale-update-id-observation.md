# 受注更新の body に含めた `id` の実測記録

## この文書の位置づけと収集条件

この文書は、受注更新 API の要求 body に含めた `id` を実 API がどう扱うかの判断のため、実 API の
挙動を記録する。現在のライブラリ仕様ではない。実測の出典はこの文書を追加・更新した各コミットであり、
[ADR 0000](adr/0000-record-architecture-decisions.md) の収集条件・検証可能性の規則に従う。

収集日は **2026-10-01（Asia/Tokyo）**。対象はテスト用ショップの、キャンセルされていない受注 1 件。
`PUT /v1/sales/{sale_id}` へ、本ライブラリの `Communicator\Request` で JSON の body を送った。

**受注の状態は変えていない。** どのリクエストも `paid` に現在の値をそのまま送った。受注 ID と、
受注に含まれる個人情報は記録しない。受注の内容は `update_date` を除いた応答全体の SHA-256 で比べた。

## 背景

0.19.0 までの `Services\Sales::update()` は、`SaleUpdateInput` が持つ `id` で path を組み立てたうえで、
同じ `id` を body の `sale` にも含めて送っていた（Issue #53）。

```json
{"sale": {"id": 1001, "paid": true}}
```

公式 OpenAPI の `PUT /v1/sales/{sale_id}` で、`sale` に定義されているのは `paid` / `point_state` /
`sale_deliveries` の 3 つで、`id` はない。受注 ID は path parameter である。

body から `id` を外すには、実 API が `id` の有無で挙動を変えないことを確かめる必要があった。

## 観測

| | body の `sale` | HTTP | 応答の `sale.id` | 実行後の受注 |
| --- | --- | ---: | --- | --- |
| 1 | `{"paid": 現在値}`（`id` なし） | 200 | path の受注 | 変化なし |
| 2 | `{"id": path と同じ受注, "paid": 現在値}`（0.19.0 までの形） | 200 | path の受注 | 変化なし |
| 3 | `{"id": 999999999, "paid": 現在値}` | 200 | path の受注 | 変化なし |

「変化なし」は、`paid` と `point_state` が変わらず、`update_date` を除いた応答全体のハッシュも一致した
ことを指す。`update_date` も 3 回とも変わらなかった。値を変えない更新は、実質的に何もしないとみられる。

**body の `id` の有無で挙動は変わらなかった**（ケース 1 と 2）。

**body の `id` は、HTTP ステータス・応答・結果のいずれにも影響しなかった**（ケース 3）。存在しない ID を
body に入れても 404 や 422 にならず、path の受注として処理された。少なくとも、更新対象の受注を探す
ために body の `id` を使っている様子はない。

ただし 3 ケースとも値を変えない更新であり、body の `id` が別の受注を指したまま値を変更したときに、
変更がどちらに入るかは直接観測していない（「確かめていないこと」を参照）。

## 確かめていないこと

- body の `id` が**存在する別の受注**を指し、かつ値を**変更**する場合に、変更が path 側の受注にだけ
  入ること。ケース 3 から path で決まると考えられるが、値を変える更新は観測していない
- `paid` 以外のフィールド（`point_state`、`sale_deliveries`）を送った場合
- 観測は 1 ショップの受注 1 件で、各ケース 1 回ずつである
