# ColorMe Shop API 決済設定応答構造の実測記録

## この文書の位置づけ

この文書は、ColorMe Shop API の実 API から収集した決済設定応答の一次情報を、ライブラリの型設計と将来の判断の根拠として保存するものであり、現在のライブラリ仕様を記述するものではない。2026-09-16 にテスト用ショップで `GET /v1/payments` を再実行し、決済6件を収集した。2026-09-17 に同じエンドポイントを再取得し、銀行振込を追加した決済7件を確認した。

同じエンドポイントは 2026-09-12 にも調査している。その時点では固定手数料の「商品代引き」だけが存在した。その後、ショップ側に「段階的代引き」と「fee_max設定代引き」を追加し、`changeable` による `cod` の構造差と、区分手数料の境界を確認するために再取得した。

ここに記録した内容は収集時点の実測結果であり、API 側の仕様変更によって古くなる可能性がある。内容を更新するときは、推測や過去の応答の流用ではなく、テスト用ショップで再収集する必要がある。

公開リポジトリへ保存するため、`account_id` は `<account_id>`、決済 ID は `<payment_id>` へ置換した。決済方法名は一般的な名称のため、そのまま掲載する。アクセストークン、契約コード、ショップ名、ショップ URL は掲載しない。

## 決済方法の一覧

2026-09-16 の全6件で、`type` は3種類だった。

| `type` | 公式上の種類 | 件数 | 実際の `name` |
| ---: | --- | ---: | --- |
| 0 | 代引き | 3 | `商品代引き`、`段階的代引き`、`fee_max設定代引き` |
| 9 | その他決済 | 2 | `郵便・コンビニ振込み`、`銀行振り込み` |
| 24 | GMO PG マルチペイメントクレジットカード | 1 | `クレジット` |

この日の応答では `financial` を持つ決済方法は0件だった。名前が「銀行振り込み」の決済は存在したが、`type=9` のその他決済であり、`financial` キーは持たなかった。銀行振込設定の応答構造は、翌日の再取得結果を以下に記録する。

## `cod` の構造と `changeable` による違い

`type=0` の3件で、`changeable` の値と手数料関連キーの有無に次の違いがあった。

| 決済方法 | `Payment.fee` | `cod` |
| --- | ---: | --- |
| 商品代引き | `300` | `{"changeable": false}` のみ。`fees`、`fee_max`、`changeable_by_total` は**キー自体がない** |
| 段階的代引き | `123` | `{"changeable": true, "fees": [[500, 200]], "fee_max": null, "changeable_by_total": false}` |
| fee_max設定代引き | `987` | `{"changeable": true, "fees": [[300, 100], [500, 70]], "fee_max": 10, "changeable_by_total": true}` |

今回の実測では、`changeable=false` の場合は手数料関連の3項目が欠損し、`changeable=true` の場合は3項目とも存在した。`changeable=false` のサンプルは1件、`changeable=true` のサンプルは2件であるため、すべてのショップや代引き設定へ一般化するには不足している。

### 商品代引き

固定手数料の商品代引きでは、`cod` は `changeable` だけを持っていた。

```json
{
  "id": "<payment_id>",
  "account_id": "<account_id>",
  "name": "商品代引き",
  "type": 0,
  "fee": 300,
  "cod": {
    "changeable": false
  }
}
```

### 段階的代引き

段階的代引きでは、3つの手数料関連キーがすべて存在した。キーの有無、値の型、`null` は実際の応答どおりである。

```json
{
  "id": "<payment_id>",
  "account_id": "<account_id>",
  "name": "段階的代引き",
  "type": 0,
  "fee": 123,
  "cod": {
    "changeable": true,
    "fees": [
      [500, 200]
    ],
    "fee_max": null,
    "changeable_by_total": false
  }
}
```

### fee_max設定代引き

上限手数料を設定した段階的代引きでは、2つの区分と最後の区分に適用する手数料が返った。

```json
{
  "id": "<payment_id>",
  "account_id": "<account_id>",
  "name": "fee_max設定代引き",
  "type": 0,
  "fee": 987,
  "cod": {
    "changeable": true,
    "fees": [
      [300, 100],
      [500, 70]
    ],
    "fee_max": 10,
    "changeable_by_total": true
  }
}
```

## `Payment.fee` と `cod.changeable` の関係

管理画面の選択状態と API 応答は次のように対応する。決済時の手数料計算自体は観測していない。

| `cod.changeable` | 管理画面の設定と `cod` の応答 | `Payment.fee` の応答 |
| --- | --- | --- |
| `false` | 一律手数料が選択され、手数料関連の3項目はキー自体がない | 商品代引きでは300円 |
| `true` | 範囲指定が選択され、`cod.fees` が返る。`cod.fee_max` は設定時に整数、未設定時に `null` が返った。`null` の場合の最終区分の挙動は未観測 | 一律手数料の入力値が残る |

`changeable=true` でも、一律手数料の入力値は `Payment.fee` に残る。実際に「段階的代引き」は `fee=123`、「fee_max設定代引き」は `fee=987` を返し、管理画面ではどちらも範囲指定が選択されていた。これらの値が決済時の手数料計算に使われるかどうかは未観測である。

## 区分手数料の設定上の境界

「fee_max設定代引き」の管理画面の設定と応答の対応から、`cod.fees` の各タプルの第1要素は、設定上、その区分に含まれない**排他的上限（未満）**であることを確認した。管理画面では最後の上限値以上の手数料が10円に設定され、応答の `cod.fee_max` も10だった。以下は設定上の区分であり、実決済での計算結果は未観測である。

| 条件 | 手数料 |
| --- | ---: |
| `0 <= 金額 < 300` | 100円 |
| `300 <= 金額 < 500` | 70円 |
| `500 <= 金額` | 10円（`fee_max`） |

したがって、`fees=[[300, 100], [500, 70]]` は、300円以下・500円以下という包含境界ではない。300円は第2区分、500円は `fee_max` の区分に入る。

## 公式 OpenAPI との差分

[公式 OpenAPI](https://api.shop-pro.jp/v1/spec/open_api.json) を 2026-09-16 に取得し、`GET /v1/payments` の200応答を確認した。公式スキーマでは、`cod.fee_max` は次のように定義されている。

```yaml
fee_max:
  description: "`fees`に設定されている区分以上の金額の場合の手数料"
  type: integer
  example: 500
```

この定義に `nullable: true` はなく、`fee_max` は `required` にも指定されていない。一方、実 API は段階的代引きで `fee_max: null` を返した。今回のテスト用ショップでは、管理画面の上限手数料を未入力にしており、この `null` は「上限手数料が未設定」であることを意味する。したがって、公式スキーマの `type: integer` かつ nullable 指定なしという記述と、実 API の値には差異がある。

また、公式 OpenAPI は `fees` の例 `[3000, 100]` を「3000円以下の場合、手数料は100円」と説明している。2026-09-16 に、管理画面の「円未満」「上記金額以上」という表記、同画面の設定値、および同日に再取得した GET 応答を突き合わせた結果、今回実測した境界値300円と500円について、`fees` の第1要素は設定上「以下」ではなく「未満」を表す。したがって、公式 OpenAPI の「3000円以下」は設定上の境界の説明として誤っている。実決済時に手数料がどの区分で計算されるかは未観測であり、本記録では確定しない。公式説明のうち、`fee_max` が最後の区分の閾値「以上」に適用される点は、管理画面の設定と応答の対応に一致する。

## `fees` の構造

公式 OpenAPI では、`fees` は配列の配列であり、内側の配列には `minItems: 2` と `maxItems: 2` が指定されている。各要素は、2つの整数からなるタプルである。公式の説明では、`[3000, 100]` は「3000円以下の場合、手数料は100円」を表す。

今回の実測値 `[[500, 200]]` については、管理画面の設定との対応から、設定上、500円未満の区分に手数料200円を対応付けていることを確認できた。また、`changeable_by_total=false` は、手数料の区分判定に決済総額ではなく商品合計額を用いる設定である。

一方、この決済方法では500円以上に使われる `fee_max` は `null` だった。そのため、500円以上の場合の手数料はこの応答から確定できない。公式 OpenAPI にも、スキーマ上は許容されていない `fee_max: null` の場合の挙動は定義されていない。

## `card` の構造

`type=24` の「クレジット」には `card` が存在し、2つのカードブランドが含まれていた。

2026-09-17 の再取得でも `card` を持つ決済は1件で、`brands` は2要素だった。`brands` と各要素の `id`、`name` に欠損・`null` はなかった。

```json
{
  "brands": [
    {
      "id": 0,
      "name": "JCB"
    },
    {
      "id": 2,
      "name": "VISA"
    }
  ]
}
```

## `financial` の構造（2026-09-17 再取得）

テスト用ショップの `GET /v1/payments`（HTTP 200）で、`type=1`（銀行振込）の決済1件に `financial` オブジェクトが存在した。前日の6件には銀行振込設定がなく、`financial` は0件だった。`type=9` の「銀行振り込み」という名前のその他決済には、今回も `financial` キーがない。決済名だけでは銀行振込設定の有無を判定できない。

該当する `financial` では、次の5項目がすべて存在し、`null` でも空文字列でもなかった。値のうち口座情報と金融機関名・支店名は公開しない。

| API キー | 観測した値の型・状態 | 管理画面の対応欄 |
| --- | --- | --- |
| `name` | 非空文字列 | 金融機関名（必須） |
| `branch_name` | 非空文字列 | 支店名（必須） |
| `kouza_type` | `"saving"` | 口座種別 |
| `kouza_number` | 非空文字列 | 口座番号（必須） |
| `kouza_name` | 非空文字列 | 口座名義（必須） |

公式 OpenAPI に定義のない `branch_number` キーも存在し、値は `null` だった。管理画面に対応する入力欄はない。この1件から、他の設定でも常に `null` になるとは判断できない。

![銀行振込決済の設定フォーム](images/financial-form.png)

*銀行振込決済の設定フォーム（ユーザー提供、2026-09-17）。画面の表示部分にショップ識別情報や口座の実値は含まれず、公開画像のメタデータも除去した。*

管理画面には、上記5項目に対応する欄のほか、決済名（必須）、決済方法ID、表示設定、説明がある。ショップオーナーの確認によると、口座種別は「普通」「当座」だけのプルダウンで、未選択にはできない。そのため、この管理画面からは5項目を未入力のまま保存できない。ただし、API があらゆるショップで5項目を必ず返すと実測したわけではない。

マスク済み応答の当該 `financial` を使った `Entities\Payment\Financial` 単体の構築と、5つの getter の呼び出しは例外なく成功した。管理画面のバリデーション導入前に作成された古い設定や、他ショップの応答は未検証であり、欠損・`null` が存在しないことまでは保証できない。

## 現在のライブラリでの扱い

現在の `Cod` エンティティでは、`fees`、`fee_max`、`changeable_by_total` のキー欠損または明示的な `null` を受け入れ、各 getter は `null` を返す。`fees` が存在する場合、2整数のタプルを `CodFee` のリストへ変換する。空配列は空リストとして保持し、不正なタプルは要素位置を示す `InvalidFieldException` になる。`getRaw()` は元のタプルとキーの有無を保持する。

`Cod::toArray()` は `fees` に `CodFee` オブジェクトのリストを含み、`toArrayRecursive()` は各要素を `upper_limit` と `fee` の連想配列へ変換する。再帰配列化では既定で `null` の項目を省略し、`false` を渡すと残す。この実装判断は [ADR 0011](adr/0011-represent-cod-fees-with-entity.md) と [ADR 0012](adr/0012-allow-nullability-from-api-observations.md) に従う。

`Financial` の5プロパティは現在、非 nullable である。今回の実測では5項目の欠損・`null` はなく、管理画面からも未入力にできないため、[ADR 0002](adr/0002-entity-nullability-from-openapi.md) と [ADR 0012](adr/0012-allow-nullability-from-api-observations.md) に照らして nullable 化する条件を満たさない。型は変更しない。`branch_number` は `Financial` に宣言されていない未知キーとして hydrate 時に無視され、`getRaw()` には残る。これは [ADR 0006](adr/0006-limit-entity-property-kinds.md) と `Entity` の既存契約に沿う。古い設定や他ショップでの応答という未検証範囲は残る。

## 再収集の概要

再収集はテスト用ショップで行い、認証情報やマスク前のレスポンスを公開リポジトリへ保存しない。

1. テスト用ショップの管理画面で、固定手数料の商品代引き、上限手数料が未設定の段階的代引き、および上限手数料を設定した段階的代引きを用意する。
2. 必要な権限を持つテスト用アクセストークンを使い、`GET https://api.shop-pro.jp/v1/payments` を実行する。調査中も認証ヘッダーをログやレポートへ出力しない。
3. HTTP ステータスとレスポンスボディを一時的な非公開領域へ保存し、トップレベルの `payments` が配列であることを確認する。
4. 各要素について、`id`、`name`、`type`、`fee` と、`cod`、`card`、`financial` の有無を記録する。`cod` では `changeable` の値ごとに `fees`、`fee_max`、`changeable_by_total` のキーの有無、値、型を区別する。`financial` では5項目と `branch_number` のキーの有無、`null`、空文字列を区別する。
5. 管理画面の「円未満」「上記金額以上」という表記と API の `fees`、`fee_max` を突き合わせ、境界が排他的上限であることを確認する。
6. 公式 OpenAPI を同日に取得し、`GET /v1/payments` の200応答スキーマと実測値を比較する。特に `required`、`nullable`、配列要素数の制約、および `fees` の境界説明を確認する。
7. 公開用文書と画像に、`account_id`、決済 ID、口座番号・名義、アクセストークン、契約コード、ショップ名、ショップ URL が含まれていないことを再確認する。画像のメタデータも確認する。

API の仕様変更を検知するため、再収集後はこの文書の件数、キーの有無、代表レスポンス、公式 OpenAPI との差分、収集日を新しい実測値で更新する。
