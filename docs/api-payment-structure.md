# ColorMe Shop API 決済設定応答構造の実測記録

## この文書の位置づけ

この文書は、ColorMe Shop API の実 API から収集した決済設定応答の一次情報を、ライブラリの型設計と将来の判断の根拠として保存するものである。2026-09-16 にテスト用ショップで `GET /v1/payments` を実行し、決済5件を収集した。

同じエンドポイントは 2026-09-12 にも調査している。その時点では固定手数料の「商品代引き」だけが存在した。その後、ショップ側に「段階的代引き」を追加し、`changeable` による `cod` の構造差を確認するために再取得した。

ここに記録した内容は収集時点の実測結果であり、API 側の仕様変更によって古くなる可能性がある。内容を更新するときは、推測や過去の応答の流用ではなく、テスト用ショップで再収集する必要がある。

公開リポジトリへ保存するため、`account_id` は `<account_id>`、決済 ID は `<payment_id>` へ置換した。決済方法名は一般的な名称のため、そのまま掲載する。アクセストークン、契約コード、ショップ名、ショップ URL は掲載しない。

## 決済方法の一覧

全5件で、`type` は3種類だった。

| `type` | 公式上の種類 | 件数 | 実際の `name` |
| ---: | --- | ---: | --- |
| 0 | 代引き | 2 | `商品代引き`、`段階的代引き` |
| 9 | その他決済 | 2 | `郵便・コンビニ振込み`、`銀行振り込み` |
| 24 | GMO PG マルチペイメントクレジットカード | 1 | `クレジット` |

`financial` を持つ決済方法は0件だった。名前が「銀行振り込み」の決済は存在したが、`type=9` のその他決済であり、`financial` キーは持たなかった。したがって、銀行振込設定の応答構造は未検証である（Issue #34 に関連）。

## `cod` の構造と `changeable` による違い

`type=0` の2件で、`changeable` の値と手数料関連キーの有無に次の違いがあった。

| 決済方法 | `cod` |
| --- | --- |
| 商品代引き | `{"changeable": false}` のみ。`fees`、`fee_max`、`changeable_by_total` は**キー自体がない** |
| 段階的代引き | `{"changeable": true, "fees": [[500, 200]], "fee_max": null, "changeable_by_total": false}` |

今回の実測では、`changeable=false` の場合は手数料関連の3項目が欠損し、`changeable=true` の場合は3項目とも存在した。ただし、各パターンのサンプルは1件ずつにすぎないため、すべてのショップや代引き設定へ一般化するには不足している。

### 商品代引き

固定手数料の商品代引きでは、`cod` は `changeable` だけを持っていた。

```json
{
  "id": "<payment_id>",
  "account_id": "<account_id>",
  "name": "商品代引き",
  "type": 0,
  "cod": {
    "changeable": false
  }
}
```

### 段階的代引き

段階的代引きでは、3つの手数料関連キーがすべて存在した。キーの有無、値の型、`null` は実際の応答どおりである。

```json
{
  "id": "<payment_id>",
  "account_id": "<account_id>",
  "name": "段階的代引き",
  "type": 0,
  "cod": {
    "changeable": true,
    "fees": [
      [500, 200]
    ],
    "fee_max": null,
    "changeable_by_total": false
  }
}
```

## 公式 OpenAPI との差分

[公式 OpenAPI](https://api.shop-pro.jp/v1/spec/open_api.json) を 2026-09-16 に取得し、`GET /v1/payments` の200応答を確認した。公式スキーマでは、`cod.fee_max` は次のように定義されている。

```yaml
fee_max:
  description: "`fees`に設定されている区分以上の金額の場合の手数料"
  type: integer
  example: 500
```

この定義に `nullable: true` はなく、`fee_max` は `required` にも指定されていない。一方、実 API は段階的代引きで `fee_max: null` を返した。今回のテスト用ショップでは、管理画面の上限手数料を未入力にしており、この `null` は「上限手数料が未設定」であることを意味する。したがって、公式スキーマの `type: integer` かつ nullable 指定なしという記述と、実 API の値には差異がある。

## `fees` の構造

公式 OpenAPI では、`fees` は配列の配列であり、内側の配列には `minItems: 2` と `maxItems: 2` が指定されている。各要素は、2つの整数からなるタプルである。公式の説明では、`[3000, 100]` は「3000円以下の場合、手数料は100円」を表す。

今回の実測値は `[[500, 200]]` であり、「500円以下なら手数料200円」を表す。また、`changeable_by_total=false` のため、手数料の区分判定には決済総額ではなく商品合計額を用いる設定である。

一方、500円を超えた場合に使われるはずの `fee_max` は `null` だった。そのため、500円を超えた場合の手数料はこの応答から確定できない。公式 OpenAPI にも、スキーマ上は許容されていない `fee_max: null` の場合の挙動や、決済直下の `fee` との関係は定義されていない。

## `card` の構造

`type=24` の「クレジット」には `card` が存在し、2つのカードブランドが含まれていた。

```json
{
  "brands": [
    {
      "id": 0,
      "name": "JCB"
    },
    {
      "id": 2,
      "name": "VISA"
    }
  ]
}
```

## ライブラリでの扱い

ライブラリのデータモデルでは、`cod.fees`、`cod.fee_max`、`cod.changeable_by_total` を nullable として扱う（Issue #28）。これにより、`changeable=false` の応答で3項目が欠損する場合と、`changeable=true` でも `fee_max` が `null` になる場合の両方を表現できる。

## 再収集の概要

再収集はテスト用ショップで行い、認証情報やマスク前のレスポンスを公開リポジトリへ保存しない。

1. テスト用ショップの管理画面で、固定手数料の商品代引きと段階的代引きを用意する。段階的代引きでは区分手数料を設定し、上限手数料を未入力にする。
2. 必要な権限を持つテスト用アクセストークンを使い、`GET https://api.shop-pro.jp/v1/payments` を実行する。調査中も認証ヘッダーをログやレポートへ出力しない。
3. HTTP ステータスとレスポンスボディを一時的な非公開領域へ保存し、トップレベルの `payments` が配列であることを確認する。
4. 各要素について、`id`、`name`、`type` と、`cod`、`card`、`financial` の有無を記録する。`cod` では `changeable` の値ごとに `fees`、`fee_max`、`changeable_by_total` のキーの有無、値、型を区別する。
5. 公式 OpenAPI を同日に取得し、`GET /v1/payments` の200応答スキーマと実測値を比較する。特に `required`、`nullable`、配列要素数の制約を確認する。
6. 公開用文書へ転記する前に、`account_id`、決済 ID、アクセストークン、契約コード、ショップ名、ショップ URL が含まれていないことを再確認する。

API の仕様変更を検知するため、再収集後はこの文書の件数、キーの有無、代表レスポンス、公式 OpenAPI との差分、収集日を新しい実測値で更新する。
