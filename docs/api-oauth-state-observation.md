# 認可応答の `state` の実測記録

## この文書の位置づけと収集条件

この文書は、認可エンドポイントが `state` パラメータをどう扱うかの判断のため、実 API の挙動を記録
する。現在のライブラリ仕様ではない。実測の出典はこの文書を追加・更新した各コミットであり、
[ADR 0000](adr/0000-record-architecture-decisions.md) の収集条件・検証可能性の規則に従う。

収集日は **2026-09-29（Asia/Tokyo）**。対象はテスト用ショップ。`localhost:8765` でコールバックを
受ける検証用のプローブを立て、認可フローを 4 回実行した。要求スコープはいずれも `read_products`
のみである。

**トークン交換は行っていない。** 認可コードを受け取った時点で捨てているため、この観測でアクセス
トークンは発行されていない。認可コード、アクセストークン、client secret は記録しない。パラメータ
の有無、長さ、値の往復だけを残す。

## 背景

[RFC 6749 §10.12](https://datatracker.ietf.org/doc/html/rfc6749#section-10.12) は、認可応答が自分の
開始したフローに対応することを確かめる CSRF 対策として `state` を推奨している。認可リクエストに
付けた値が、コールバックにそのまま返ることが前提である。

しかし**公式 OpenAPI は `state` に一切触れていない**。OAuth の手順は `info.description` にのみ記述
があり、認可 URL のパラメータ表は `client_id` / `response_type` / `scope` / `redirect_uri` の 4 つ
だけを挙げる。`info.description` 中に `state` の語は 1 度も現れない。仕様全体を走査すると `state`
という名前のフィールドは 4 件あるが、いずれもショップのアカウント状態（`shop.state`）とテンプレート
の利用状況（`template.state`）で、OAuth とは無関係である。

したがって「`state` を付ければ返ってくる」は RFC 上の期待にすぎず、カラーミーで確かめられていな
かった。`Services\OAuth::getUrl()` に `state` を追加してよいかを決めるため、実測した。

## 観測

各ケースで 1 変数だけを変えた。

| | 送った `state` | 認可画面での操作 | 返ったパラメータ | 値の一致 |
| --- | --- | --- | --- | --- |
| A | hex 32 文字 | 承認 | `code`, `state` | 一致 |
| B | `probe:a+b/c=d&e f~日本`（24 バイト） | 承認 | `code`, `state` | デコード後に一致 |
| C | hex 32 文字 | **拒否** | `error`, `error_description`, `state` | 一致 |
| D | 1024 文字 | 承認 | `code`, `state` | 一致 |

**カラーミーの認可エンドポイントは `state` を受理し、成功・拒否のいずれでもそのまま返す。**
公式ドキュメントに記載がないだけで、RFC 6749 の想定どおりに動作する。

いずれのケースでも、返ったパラメータは上表のものだけだった。ライブラリが解釈すべき未知の
パラメータは付かない。認可コードは 4 回とも 64 文字だった。

### 値は往復するが、エンコードは書き換えられる（ケース B）

記号と非 ASCII を含む値を送ったところ、クエリ文字列の見た目が変わって返った。

```
送信（rawurlencode）: probe%3Aa%2Bb%2Fc%3Dd%26e%20f~%E6%97%A5%E6%9C%AC
返却（実測）:         probe%3Aa%2Bb%2Fc%3Dd%26e+f%7E%E6%97%A5%E6%9C%AC
```

差異は 2 か所で、空白が `%20` から `+` に、チルダが `~` から `%7E` になっている。カラーミー側が
値を一度デコードし、`application/x-www-form-urlencoded` の規則で再エンコードして返していると
解釈できる。

**デコード後の値は送った文字列と完全に一致する**（24 バイト、非 ASCII も保たれる）。したがって
照合はデコード後の値で行う必要があり、クエリ文字列のバイト列を比較すると一致しない。PHP の
`$_GET` は自動でデコードするため通常は問題にならないが、生のクエリを自前で扱う場合は踏む。

### 拒否時の応答（ケース C）

認可画面で拒否すると、次の 3 つが返った。`code` は付かない。

| パラメータ | 値 |
| --- | --- |
| `error` | `access_denied` |
| `error_description` | `認可をキャンセルしました。` |
| `state` | 送った値と一致 |

`error` は [RFC 6749 §4.1.2.1](https://datatracker.ietf.org/doc/html/rfc6749#section-4.1.2.1) が
定める標準の値である。

一方 `error_description` は日本語で返る。RFC は同項でこの値を US-ASCII の範囲
（`%x20-21` / `%x23-5B` / `%x5D-7E`）に限っているため、**カラーミーの応答は RFC の規定から外れる**。
クエリ文字列としては UTF-8 を percent-encode して送られるため伝送自体は成立するが、この値を表示
する側は文字コードの扱いに注意が要る。

**エラー応答にも `state` が付くことは、コールバックの実装順序に影響する。** エラーの内容を表示
する前に `state` を検証できる。逆に言えば、検証を後回しにすると未検証の応答を画面に出すことに
なる。`examples/oauth-callback/` はこの順序を採っている。

### 長さ（ケース D）

1024 文字の値をそのまま返した。切り詰めも拒否もない。上限がどこにあるかは確かめていない。実用
される長さ（乱数 16〜32 バイトの hex、あるいは署名付きトークン）では問題にならないと判断し、
これ以上の探索はしていない。

## 確かめていないこと

- `state` の長さの上限。1024 文字までは問題ないことしか確認していない
- 空文字の `state=` を送ったときの挙動。これはライブラリ側で弾く判断としたため観測していない
  （[ADR 0020](adr/0020-accept-state-in-authorization-url.md)）
- `state` を付けずに認可した場合に応答へ `state` が現れないこと。ケース A〜D はすべて付けている
- 同じ `state` を再利用したときの扱い。認可サーバーは state を保持しないため関係しないと考えている
- 観測はいずれも 1 ショップ・1 回である
