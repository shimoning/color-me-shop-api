# ADR 0020: 認可 URL に state を受け取る

- 状態: 採用
- 決定日: 2026-09-29

## 文脈

`Services\OAuth::getUrl()` は認可 URL を `client_id` / `redirect_uri` / `response_type` / `scope`
だけで組み立てており、OAuth 2.0 の `state` パラメータを渡す手段がなかった。

`state` は認可応答が自分の開始したフローに対応することを確かめるための値で、CSRF 対策として
[RFC 6749 §10.12](https://datatracker.ietf.org/doc/html/rfc6749#section-10.12) が推奨している。
これがないと、第三者のページが無関係な認可応答を利用者のコールバックへ混入させられる。

利用者が `state` を使うには、`getUrl()` の戻り値へ自分で `&state=...` を連結するか、認可 URL を
自前で組み立てるしかなかった。前者は `examples/oauth-callback/` が実際に採っていた方法である。
Issue #85 はこの制約を切り出したものである。

`state` を組み込めるかは自明ではなかった。**公式 OpenAPI は `state` に一切触れていない。** OAuth の
手順は `info.description` にのみ記述があり、認可 URL のパラメータ表は `client_id` /
`response_type` / `scope` / `redirect_uri` の 4 つだけを挙げる。`state` を送っても返るとは限らず、
返らなければライブラリが引数を受け取っても利用者は照合できない。

2026-09-29 に認可フローを 4 回実行して実測した。詳細は
[認可応答の `state` の実測記録](../api-oauth-state-observation.md)にある。出典: `d3e0ec8`。

- カラーミーの認可エンドポイントは `state` を受理し、コールバックにそのまま返す
- **拒否したときのエラー応答（`error=access_denied`）にも `state` が付く**
- 値は一度デコードされ再エンコードされて返る。クエリ文字列のバイト列は送信時と一致しないが、
  デコード後の値は完全に一致する
- 1024 文字でも切り詰められない。記号と非 ASCII も保たれる

## 判断

- `getUrl()` に任意引数を追加し、`getUrl(Scopes $scopes, ?string $state = null): string` とする。
  `null`（既定）のときは `state` パラメータを付けないため、既存の呼び出しは壊れない。
  実測で往復が確認できたため、引数を受け取る意味がある。出典: `0a3fbba`。
- **`state` の生成と保存は利用者の責務とし、ライブラリは受け取って URL に載せるだけにする。**
  保存先はセッション・クッキー・署名付きトークンなどフレームワークに依存し、ライブラリが選ぶと
  利用者の選択肢を狭める。出典: `0a3fbba`。
- 空文字を渡された場合は `Exceptions\ParameterException` を投げる。`state=` という空の値を送っても
  照合の役に立たず、利用者の取り違え（未初期化の変数を渡したなど）である可能性が高い。黙って
  送ると CSRF 対策をしたつもりで機能しない状態になる。出典: `0a3fbba`。
- **コールバックの照合を補助するヘルパーは設けない。** `exchangeCode2Token()` は認可コードだけを
  受け取るままにする。照合はリクエストオブジェクトとセッションに触れる処理であり、ライブラリが
  HTTP 層の抽象を持ち込まずに実装できない。出典: `0a3fbba`。
- 公式仕様に記載がない点と実測でわかった差異は `getUrl()` の PHPDoc に明記する。とくに「照合は
  デコード後の値で行う」ことと「拒否時にも `state` が返る」ことを書く。
  [CONTRIBUTING.md](../../CONTRIBUTING.md) の規約に従う。出典: `0a3fbba`。
- `examples/oauth-callback/` は新しい引数を使う形に直し、自前の連結をやめる。出典: `0a3fbba`。

## 代替案と却下理由

- **ライブラリが `state` を生成して返す案**（`getUrlWithState(): array{url: string, state: string}`
  のような形）は、乱数の質をライブラリが保証できる。しかし保存は結局利用者が行うため、生成だけを
  引き取っても責務が中途半端に分かれる。戻り値が配列かタプル状の値オブジェクトになり、既存の
  `getUrl()` と 2 つの入口ができる。`random_bytes()` は PHP 標準であり、利用者が書く行数はほとんど
  変わらないため採用しない。
  なお同じ「別メソッドを足す」形は、レビューで別の理由から再提案された。既存シグネチャを保ったまま
  state 対応のメソッドを分ければ、サブクラスのオーバーライドを壊さずに済むという指摘である。
  継承の非互換は事実だが（後述の帰結を参照）、2 つの入口ができる欠点はここに書いたとおりであり、
  `Client` のファサードも同様に二重化する。避けたい非互換が互換性の契約の外にあることから、
  この理由でも採用しない。
- **空文字を黙って無視して `state` なしの URL を返す案**は、例外を投げないぶん扱いやすい。しかし
  利用者は `state` を付けたつもりでいるのに CSRF 対策が効かない URL を受け取ることになり、失敗が
  表に出ない。「エラーは握りつぶさず、意味のあるメッセージ付きで処理する」方針に反するため採用
  しない。
- **コールバックの照合ヘルパーを設ける案**（`verifyState($given, $expected)` のような静的メソッド）
  は、`hash_equals()` を直接使うより意図が伝わる。しかし中身は 1 行の比較でしかなく、保存した値を
  どこから取り出すかという肝心の部分は利用者に残る。公開 API を増やすだけの価値がないため採用
  しない。照合の要点は `getUrl()` の PHPDoc とサンプルで示す。
- **`getUrl()` を変えず、利用者に連結を続けさせる案**は、変更が不要である。しかし連結する際の
  エンコード（`rawurlencode` の要否）を利用者が毎回判断することになり、`getUrl()` が
  `PHP_QUERY_RFC3986` でエンコードしている事実と噛み合わない。CSRF 対策という基本的な要件を
  ライブラリが支えないままになるため採用しない。
- **`state` を必須引数にする案**は、対策を忘れさせない。しかしすべての既存の呼び出しが壊れる。
  `urn:ietf:wg:oauth:2.0:oob` を使う WebView のように、CSRF の文脈が異なる使い方もある。破壊的
  変更に見合う利益がないため採用しない。

## 帰結

利用者は `state` を生成・保存したうえで `getUrl()` に渡し、コールバックで照合できるようになる。
認可 URL の組み立てを自前で行う必要がなくなる。

任意引数の追加であり、**呼び出し側は引数も戻り値も変わらない。**

ただし継承については互換ではない。`Services\OAuth` と `Client` は `final` ではないため、
`getUrl()` または `getOAuthUrl()` を旧シグネチャでオーバーライドしているサブクラスがあると、
クラスの読み込み時に致命的エラーになる。PHP 8.1 で実測した文言は
`Declaration of Child::getUrl(Scopes $scopes): string must be compatible with
Parent::getUrl(Scopes $scopes, ?string $state = null): string` である。子が親の受け付ける呼び出しを
受け付けなくなるためで、任意引数を足す変更に一般に付きまとう。

このライブラリが想定する拡張点は、[ADR 0001](0001-testing-boundaries-and-http-client-injection.md)
が定めた `ClientInterface` のコンストラクタ注入であり、Service や `Client` のサブクラス化ではない。
README にも CONTRIBUTING.md にもオーバーライドを支える記述はないため、**この非互換は互換性の契約の
外にある**と判断する。とはいえ気づきうる影響であるため、リリースノートの `契約変更 (要注意)` に
「サブクラスで旧シグネチャのオーバーライドをしている場合のみ」という限定付きで挙げる。

`state` の生成・保存・照合は引き続き利用者の責務である。ライブラリは「渡された値を URL に載せる」
ところまでしか担わないため、利用者が保存と照合を実装しなければ CSRF 対策にはならない。この境界は
`getUrl()` の PHPDoc と `examples/oauth-callback/` で示す。

実測は 1 ショップ・4 回である。公式ドキュメントに記載がないパラメータに依存するため、カラーミーが
`state` の返却をやめた場合、利用者の照合は失敗する。README とサンプルが示す形で照合していれば、
失敗した時点でコードの交換を止めるため、黙って CSRF 対策なしになることはない。認可フローが使えなく
なるだけである。逆に、照合の失敗を無視する実装にしていた場合にのみ、対策がないまま動き続ける。
いずれにせよライブラリ側で吸収できる問題ではない。
