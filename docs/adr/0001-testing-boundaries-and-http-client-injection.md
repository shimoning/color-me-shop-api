# ADR 0001: テスト境界と HTTP クライアント注入

- 状態: 採用
- 決定日: 2026-09-07

## 文脈

HTTP オブジェクトを内部で直接生成していたため、Service 層を外部通信なしで検証できなかった。
また、既存利用者の公開シグネチャを保ったままテスト容易性を確保する必要があった。

## 判断

- 動作している既存コードは、明確な目的なしにリファクタしない。必要な変更も公開契約を保つ
  最小範囲に限定する。出典: `f4336bf`。
- PHPUnit `^10.5` をテスト基盤とする。PHP 8.1 をサポートしつつ利用できる世代だからである。
  出典: `81cf6bb`。
- 既存挙動の変更を伴うリファクタでは、先に仕様化テストで契約を固定する。新しい振る舞いは
  Red-Green-Refactor で追加する。出典: `f4336bf`。
- 自動テストは実 API や `.env` に依存させず、固定フィクスチャと差し替え可能な HTTP
  クライアントを使う。出典: `f4336bf`。
- Service に単一の `Request` を注入せず、Guzzle の `ClientInterface` を任意注入する。
  認証や本文形式を含む `RequestOptions` は呼び出しごとに異なり、`Request` の共有では
  正しい境界を作れないためである。既存の必須引数は変えない。出典: `68ab63d`、`1556f38`。
- 公開ファサードの `Client` にも `ClientInterface` を任意注入し、そこから生成する全 Service
  へ同じインスタンスを伝播する。既存の呼び出しを壊さず、ファサード経由の通信も外部通信なしで
  検証可能にするため、第2引数として追加する。出典: `8fce5a9`、`1b68f8d`。
- `Client` は Service をキャッシュせず、呼び出しごとに生成する。Service はアクセストークンと
  HTTP クライアントを保持しており、キャッシュすると別の `Client` が以前のトークンを持つ Service
  を共有し得るためである。出典: `8fce5a9`。
- アクセストークンを受け取る `Client` の公開メソッドでは、トークン引数の `null` のみを「未指定」
  とし、空文字を含む非 `null` 値は明示指定として扱う。空文字は検証で `ParameterException` とし、
  保持中の旧トークンへフォールバックさせない。マルチテナント利用で別テナントの認証情報を黙って
  使うより、安全に失敗させるためである。出典: `1b68f8d`。
- CI と PHPStan level 3 による静的解析を継続し、`composer check` を共通の検証入口とする。
  level 4 以降を一律に満たすために、契約を固定する意図的なテストのアサーションや防御コードを
  損なわず、`baseline` や `ignoreErrors` で指摘を隠さないためである。レベルを引き上げる場合は、
  `src` と `tests` で解析レベルを分ける構成を選択肢とする。出典: `7db9ad1`、`4293def`。
- `composer validate` は `--strict --no-check-version` で実行する。`composer.json` の `version`
  フィールドを置くかはパッケージ管理方針であり、自動テストを通すために変更すべきではないので、
  その警告だけを検査対象外とする。出典: `b5ab9ed`、`4293def`。

## 現在の状態

基底 `Services\Service` を継承する 6 サービス（`Customer` / `Delivery` / `Payment` / `Product` /
`Sales` / `Shop`）では、HTTP クライアントの保持と `Request` 生成が集約されている。
`OAuth` は基底クラスの対象外で、現在も自クラス内で直接 `Request` を生成するが、同じく
`ClientInterface` を任意注入できるため、テスト時の注入境界は維持されている。
出典: `3cfe677`、`1f7520f`。

公開ファサードも、注入された HTTP クライアントを全 Service へ伝播し、Service を都度生成する。
トークンの `null` と空文字を区別する挙動は現行の `Client` で維持されている。一方、Service 層には
同等の検証がなく、`Services\Service` は空文字を受け入れて認証情報に使用する。これは意図的な契約
として採用したものではなく、未対応の現状である。PHPStan level 3 と抑制を使わない方針も、現行の
`phpstan.neon`、`composer.json` で維持されている。

アクセストークン検証に関するこの判断は、[ADR 0005](0005-consolidate-access-token-validation-into-service.md)
により更新された。

ページ形式のレスポンス生成は `Page::build()` に集約され、ページネーションの欠損と不正値は
`MissingPaginationException` と `InvalidPaginationException` で区別する。これにより、固定すべき
HTTP 応答契約が明示された。出典: `ae36b5a`、`2e13412`、`ead46f7`。

## 帰結

実通信を行う結合テストはこのリポジトリの自動テスト範囲に含めない。公開シグネチャを変更する
場合は、互換契約を先にテストで明示し、別の判断として評価する。
