# ADR 0038: 商品一覧の sort を値オブジェクトで扱う

- 状態: 採用
- 決定日: 2026-10-08

## 文脈

商品一覧の検索条件 `Entities\Product\SearchParameters` の `sort` は `?string` で、利用者が書いた文字列
（`'-sales_price,make_date'` など）をそのまま送っていた。カラム名と昇順・降順（先頭の `-`）が 1 つの文字列に混ざり、
組み立ても読み取りも利用者に任されていた。

公式 OpenAPI の `GET /v1/products` の `sort` は文字列で、先頭の `-` で降順、カンマ区切りで複数指定でき、指定可能な
カラムを 5 つ挙げている。2026-10-08 に実 API で確かめたところ、次のとおりだった。詳細は
[商品一覧の sort の実測記録](../api-product-sort-observation.md)にある。出典: `dedbad9`。

- 仕様にあるカラムは、`-` の有無で昇順・降順に並んだ
- 仕様にない値（仕様にないカラム名、空文字、`-` だけ、`--sales_price`）は、エラーにならず既定の並びと同じ結果に
  なった
- カンマの後に空白を入れると、空白なしと同じ並びにならなかった

## 判断

- **並び順を、汎用の値オブジェクト `Values\Sort` で表す。** `Values\Limit` と同じく、特定の API に寄らない値
  オブジェクトとして `Values` の直下に置く。1 つの `Sort` は、カラム名（文字列）と向き（`Constants\SortDirection`）を
  1 組だけ持つ。`get()` は API に送る形（昇順は `field`、降順は `-field`）を返す。利用者の指定による。出典: `2d73fd1`。
- 向きは省略でき、省略すると昇順とする。向きを省略してカラム名を `-` で始めると、先頭の `-` を取り除いて降順と
  する。利用者の指定による。出典: `2d73fd1`。
- `-` で始まるカラム名と向きを一緒に渡すと、意図があいまいになるため `ParameterException` で拒否する。出典: `2d73fd1`。
- **カラム名そのものは検証しない。** 利用者の指定による。ただし形式として、空のカラム名、`-` を取り除いた後も
  `-` で始まるもの、カンマや空白を含むものは拒否する。カンマは複数指定の区切りと紛れ、空白は実 API の並びを
  変えたためである。出典: `dedbad9`、`2d73fd1`。
- **商品の検索条件の `sort` は、`Sort` 1 つか `Sort` の配列で受け、各 `get()` を空白なしのカンマでつないで送る。**
  文字列での指定は受け付けない。文字列と `Sort` の両方を受ける変換を足すと仕組みが煩雑になるためである。利用者の
  指定による。出典: `2d73fd1`。
- これを基底 `Entities\Entity` の `FIELD_TYPES` で実現するため、次のオプションを加える。いずれも明示したフィールド
  だけに効き、ほかのフィールドの挙動は変えない。出典: `2d73fd1`。
  - `instance`: 値オブジェクトのフィールドで、宣言したクラスのインスタンスだけを受け付ける。値オブジェクトの
    フィールドは生の値で指定し、インスタンスは受け付けないという従来の契約は、`instance` を指定しないフィールドで
    そのまま保つ
  - 配列を区切り文字でつなぐ `delimiter`（`902a1cb` で加え、`1a19d3c` で整数か文字列の配列に限ったオプション）を、
    `instance` を指定した値オブジェクトの配列にも使えるようにし、各要素の `get()` をつなぐ

## 代替案と却下理由

- **カラム名を enum で限定する案**は、指定できないカラムを送信前に拒否できる。しかし利用者の指定により、カラム名は
  文字列で受け、検証しない。
- **1 つの `Sort` に複数のキーを持たせる案**は、検索条件の型が単純になる。しかし利用者の指定により、`Sort` は 1 組
  だけを持ち、複数の指定は検索条件で `Sort` の配列として受ける。
- **文字列（`'-sales_price'`）も検索条件で受け付ける案**は、移行が楽になる。しかし文字列と `Sort` の両方を受ける
  仕組みが煩雑になるため、受け付けない。
- **商品の検索条件だけで `toArrayRecursive()` を上書きする案**は、基底の仕組みを変えずに済む。しかし検索条件ごとの
  上書きをやめて基底の `FIELD_TYPES` にまとめた方針から外れる。

## 帰結

並び順のカラム名と向きを、利用者が分けて組み立て、読み取れるようになる。

次の点が変わる。破壊的変更のため、次のマイナーバージョンで行う。

- 商品の検索条件に `sort` を文字列で渡しているコードは、`InvalidFieldException` になる。`Sort` に書き換える必要がある
- 商品の検索条件の `toArray()` の `sort` は、文字列から `list<Sort>` になる。送信するクエリ（`toArrayRecursive()`）は
  従来どおりカンマ区切りの文字列である
- カラム名を検証しないため、指定できないカラム名を渡してもエラーにならない。実 API は既定の並びを返す（2026-10-08 の
  観測）
- 値オブジェクトのインスタンスを受け付けるフィールドが、`instance` を指定したものに限って生まれる
