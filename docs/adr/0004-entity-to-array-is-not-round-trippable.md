# ADR 0004: Entity の `toArray()` は往復可能な直列化ではない

- 状態: 採用（既知の制約）
- 決定日: 2026-09-11

## 文脈

`Entity::toArray()` は配列化対象の宣言済みプロパティを出力し、API レスポンスになかった項目も
`null` として含める。アンダースコアで始まる内部プロパティは対象外である。出力を同じ Entity の
コンストラクタへ渡すと、非 null 許容プロパティへの `null` 代入によって `TypeError` になる。また、
設定済みのネストした Entity や value オブジェクトもそのまま出力する一方、コンストラクタは raw な
配列やスカラーから再構築するため、値が揃っていても再入力できない場合がある。

## 判断

`toArray()` は現在値を確認するための表現とし、コンストラクタへ戻せる直列化形式であることを
保証しない。出典: `7a9e566`。

API 名からプロパティ名への変換と、その逆変換は対称ではない。自動変換で元に戻せないフィールドは、
一律の変換規則を変えず、Entity ごとの `FIELD_NAMES` 対応表で入出力の両方を補正する。
出典: `7a9e566`。

代替案として数字の前へ一律にアンダースコアを入れる規則も検討したが、`name1` や
`option1_value` のように数字が元から区切られていない API 名を `name_1` などへ変えてしまうため
採用しない。対応表は例外を明示する手間がある一方、既に正しいフィールド名を維持できる。
出典: `7a9e566`。

対応表の導入で `toArray()` の既存キーと API 名が競合する場合は、誤った既存キーとの互換性より
API 名を優先する。例えば `shop_mail1` は `shop_mail_1` に変わるが、前者は API に存在しないため、
この互換性変更を受け入れる。出典: `7a9e566`。

## 現在の状態

この制約は未解決である。現行の `Entity::toArray()` も未設定値へ `null` を補い、コンストラクタは
入力に含まれる `null` を非 null 許容プロパティへ代入する。例えば空データから作った `Sale` の
`toArray()` を `Sale` へ再入力すると、`$id` への代入で `TypeError` になる。

設定済みのオブジェクトも再帰変換されない。例えば `Card::toArray()` の `brands` には `Brand` が
そのまま残るが、再入力時は raw な配列を想定して各値を `Brand` のコンストラクタへ渡すため、
`Entity::__construct(array $data)` の型と一致せず `TypeError` になる。

非対称なフィールド名への対応は現行実装でも有効である。`Entity` のコンストラクタと
`apiFieldName()` は `FIELD_NAMES` を自動変換より優先し、`Shop` が `shop_mail_1` と
`shop_mail_2` の対応を定義している。

## 帰結

呼び出し側は `toArray()` を Entity 再構築用の入力として扱わない。往復可能性が必要になった
場合は、未初期化と明示的な `null` を区別する形式、または用途を分けた serializer を別途設計する。
フィールド名の例外が増えた場合は、共通規則を広げず該当 Entity の `FIELD_NAMES` に追加する。
