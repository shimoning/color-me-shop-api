# ADR 0040: 値オブジェクトのフィールドでインスタンスも受け付ける

- 状態: 採用
- 決定日: 2026-10-09

## 文脈

`Entities\Entity` の `FIELD_TYPES` で型を宣言したフィールドは、宣言の種類によってインスタンスの扱いが違っていた。

- enum（`enum`）: 生の値（バッキング値）と、同じ enum のインスタンスを受け付けていた
- Entity（`entity`）: 生の値（連想配列）と、インスタンスを受け付けていた。要求側では、`RequestEntity` でない
  インスタンスを `getRaw()` から作り直す（[ADR 0024](0024-model-sale-create-api.md)）
- 値オブジェクト（`value`）: 生の値だけを受け付け、インスタンスは拒否していた

[ADR 0038](0038-represent-sort-with-value-object.md) で商品一覧の `sort` を値オブジェクトで扱ったとき、`Values\Sort` の
インスタンスを受け付ける形をいったん実装した。しかし値オブジェクトのフィールドのうち `sort` だけを例外にすることに
なり、影響が大きいため取り下げ、値オブジェクトのインスタンスの扱いは enum・Entity とあわせて別に判断することに
した。

また、[ADR 0036](0036-validate-limit-per-api.md) と [ADR 0039](0039-validate-product-sort-fields.md) で、API ごとの制約を
値オブジェクトの子クラス（`Values\Product\Limit`、`Values\Product\Sort`）で表すようにした。利用者が基底の
`Values\Limit` や汎用の `Values\Sort` のインスタンスを作って渡す場面がありうる。

## 判断

- **値オブジェクトのフィールドでも、生の値に加えてインスタンスを受け付ける。** enum と Entity と揃える。`FIELD_TYPES`
  に新しいオプションは足さず、すべての値オブジェクトのフィールドで受け付ける。利用者の指定による。出典: `d13a7fa`。
- 宣言したクラスか、その子クラスのインスタンスは、そのまま使う。値オブジェクトは不変なので作り直さない。
  出典: `d13a7fa`。
- **宣言したクラスの親クラスのインスタンスは、`get()` の値から宣言したクラスで作り直し、制約を検証し直す。**
  たとえば商品の検索条件に基底の `Values\Limit(80)` を渡すと、商品の上限 50 を超えるため拒否する。`get()` の値を
  コンストラクタが受け付けないクラスの組み合わせでは、作り直せずに拒否される。出典: `d13a7fa`。
- 宣言したクラスと継承関係のない値オブジェクト（`Values\Value` を実装するもの）のインスタンスは、コンストラクタに
  渡す前に拒否する。コンストラクタがそのオブジェクトを受け付ける場合（`DateTimeInterface` を継承した値オブジェクトを
  `Values\DateTime` のフィールドに渡すなど）でも拒否する。出典: `cde4a45`。
- 値オブジェクトでないオブジェクトは、従来どおりコンストラクタに渡し、受け付けるかどうかはコンストラクタに任せる
  （`Values\DateTime` は `DateTimeInterface` を受け付ける）。出典: `cde4a45`。
- **要求側では、検証に通らない値を保持した `Values\FallbackValue` のインスタンスを拒否する。** 生の値で渡した
  ときと同じく、要求側は厳密に検証するという方針に揃える。enum のフォールバックの case を要求側で拒否するのとも
  揃う。応答側では従来どおり受け付ける。利用者の指定による。出典: `d13a7fa`。
- 配列のフィールドは、要素ごとに生の値とインスタンスを混在して受け付ける。出典: `d13a7fa`。

## 代替案と却下理由

- **値オブジェクトのフィールドは生の値だけを受け付けるままにする案**は、変更がない。しかし enum と Entity は
  インスタンスを受け付けており、宣言の種類によって受け付け方が違うままになる。
- **`FIELD_TYPES` のオプションで、インスタンスを受け付けるフィールドを明示する案**（0.28.0 の作業で試した
  `instance`）は、影響を限れる。しかしフィールドごとに受け付け方が違い、利用者が見分けにくい。
- **親クラスのインスタンスもそのまま使う案**は、作り直しが要らない。しかし `Values\Product\Limit` の上限など、
  子クラスで表した API ごとの制約を通らずに送ることになる。
- **要求側でも検証に通らない `FallbackValue` のインスタンスを受け付ける案**は、応答で受け取った値をそのまま
  書き戻せる。しかし実 API が拒否する値を送ることになり、生の値で渡したときと扱いが違う。

## 帰結

値オブジェクト・enum・Entity のどのフィールドでも、生の値とインスタンスのどちらでも渡せるようになる。

次の点が変わる。

- これまで `InvalidFieldException` になっていた値オブジェクトのインスタンスが、受け付けられる。インスタンスが拒否
  されることを前提にしたコードは、挙動が変わる
- 親クラスのインスタンスは作り直されるため、`toArray()` の値は渡したインスタンスと別のインスタンスになる
- 応答から取り出した、検証に通らない値を持つ `Furigana` などを要求側に渡すと拒否される
- 宣言したクラスと継承関係のない値オブジェクトは、コンストラクタが受け付ける型であっても拒否される。これまでは
  コンストラクタに渡していたため、たとえば `DateTimeInterface` を継承した利用者の値オブジェクトを `Values\DateTime`
  のフィールドに渡すと受け付けられていたが、拒否されるようになる。値オブジェクトでない `DateTimeInterface` は
  従来どおり受け付ける
