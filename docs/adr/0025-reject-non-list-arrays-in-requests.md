# ADR 0025: 要求側の配列フィールドでキーが連番でない配列を拒否する

- 状態: 採用
- 決定日: 2026-10-02

## 文脈

[ADR 0018](0018-unify-array-annotations-without-list-validation.md) は、配列フィールドの注釈を `list<…>` に
統一したうえで、**リスト形状（キーの連番性）は実行時に検証も正規化もしない**と決めた。根拠は、実 API の
応答で配列を返す 22 キー・のべ 149 箇所がすべて JSON 配列で、オブジェクト形状を 1 つも観測しなかった
ことである。この判断は主に応答側を想定していた。

要求側では事情が異なる。利用者が `unset()` や絞り込みでキーの飛んだ配列を組み立てると、PHP の
`json_encode()` はそれを JSON 配列ではなく JSON オブジェクトにする。PR #92（受注作成）の Copilot の
レビューで、次のように送られることが分かった。

```
受注作成: {"sale":{"details":{"1":{"product_id":2,"product_num":1}},"payment_id":1}}
受注更新: {"sale":{"sale_deliveries":{"3":{"name":"x"}}}}
```

必須項目の確認も通ってしまい、API が配列を要求する位置にオブジェクトが送られる。受注更新の問題は
受注作成より前からあった。

一方、`Product\ProductInput` はすでに `group_ids` と `variants` で `array_is_list()` を確かめ、連番でない
配列を `InvalidFieldException` にしていた。要求側の扱いは揃っていなかった。

`FIELD_TYPES` は、[ADR 0023](0023-validate-scalar-array-elements-via-field-types.md) 以降、入れ子の Entity /
値オブジェクト / enum の配列に加えてスカラー配列も宣言する。どのフィールドが配列かを基底 `Entity` が
知る手段がそろっている。

## 判断

- **要求文脈（`RequestEntity` とその入れ子）で、`FIELD_TYPES` に `array` と宣言したフィールドに、キーが
  連番でない配列が来たら `InvalidFieldException` にする。** 期待する型は `list<型>` と表す。`ProductInput` の
  既存の拒否と同じ形である。出典: `2cec1d0`。
- 検査は要素の変換より前に行い、要素の型の誤り（`forArrayElement()`）と区別できるメッセージにする。
  空配列は連番として扱う。外側が配列でない値は、従来どおり外側の型の検証に任せる。出典: `2cec1d0`。
- **応答側は変えない。** ADR 0018 の判断（応答のリスト形状は検証しない）を保つ。実 API の応答で連番で
  ない配列は観測していない。出典: `9808f85`、`2cec1d0`。
- 入れ子の Entity の配列に、**すべてのキーが文字列**の連想配列を渡した場合は、「単体の Entity を 1 つ
  包む」既存の扱いを残す。整数キーと文字列キーが混ざった配列は、形の誤りとして拒否する。値オブジェクト /
  enum / スカラーの配列にはこの扱いがないため、文字列キーの配列も拒否する。出典: `2cec1d0`、`1a9c277`。
- **setter でも同じ規則を適用する。** setter は基底の組み立て処理を通らずに直接代入するため、そのままでは
  キーの飛んだ配列を受け付けてしまう。判定とメッセージは基底のヘルパーにまとめ、配列のフィールドに
  代入する setter（現時点では `SaleUpdateInput::setSaleDeliveries()` だけ）から呼ぶ。今後の setter の漏れは
  横断テストで検出する。出典: `1a9c277`。
- 要求文脈で、`RequestEntity` でない組み立て済みの子を生データから組み立て直す経路
  （[ADR 0024](0024-model-sale-create-api.md)）でも、この規則を適用する。出典: `2cec1d0`。
- `ProductInput` の個別の拒否処理（`group_ids`、`variants`）は残す。`FIELD_TYPES` に宣言のないフィールド
  には基底の規則が効かないためである。出典: `2cec1d0`。

ADR 0018 の「リスト形状は検証しない」という判断のうち、要求側については本 ADR で更新する。応答側の
判断はそのまま残る。

## 代替案と却下理由

- **拒否せず、`array_values()` でキーを振り直して送る案**は、利用者がキーを気にせず絞り込んだ配列を
  渡せる。ADR 0018 が振り直しを採らなかった理由（どのフィールドを list とするかの宣言が要る）も、
  `FIELD_TYPES` で解消している。しかし次の欠点があり、利用者と協議のうえ、いったん拒否で揃える
  ことにした。
  - 呼び出し側の `unset()` の誤りなどが、例外にならず黙って送られる
  - 並びがキーの順ではなく、配列に入れた順になる（`[2 => A, 0 => B]` は `[A, B]`）
  - `ProductInput` を「拒否」から「受け付け」に変えることになり、既存の拒否を確かめるテストの変更が要る
  - `getRaw()` と送信内容のキーがずれる
- **受注作成の入力だけで個別に拒否する案**は、変更が受注作成に閉じる。しかし同じ問題のある受注更新や
  検索条件が残り、今後の入力クラスでも同じ書き忘れが起きうる。基底の規則にすれば宣言だけで効く。
- **応答側も含めて拒否する案**は、要求側と応答側の扱いが揃う。しかし実 API の応答で連番でない配列は
  観測しておらず、もし返ってきた場合に Entity の構築が失敗する。ADR 0018 が応答側の検証を採らなかった
  理由がそのまま当てはまる。

## 帰結

要求側の配列フィールドは、連番の配列でなければ受け付けない。JSON オブジェクトや飛び番のクエリとして
送られることはなくなる。今後の入力クラスでも、`FIELD_TYPES` に配列と宣言するだけで効く。

例外として、入れ子の Entity の配列に、すべてのキーが文字列の連想配列を 1 つ渡した場合は、後方互換の
ため要素 1 件として包んで受け付ける。整数キーと文字列キーが混ざった配列は拒否する。

次の挙動が変わる。破壊的変更のため、次のマイナーバージョンで行う。

- 入力クラスと検索条件で、配列フィールドに連番でない配列（`[1 => …]` や `['a' => 1]` のスカラー配列など）
  を渡すと、生成時や setter での設定時に `InvalidFieldException` になる。これまでは受け付けて送っていた。呼び出し側で
  `array_values()` などを通す必要がある

応答を入力に作り替える経路（`SaleUpdateInput::convert()`、応答の Entity を入力の入れ子に渡す場合）では、
元の応答の配列が連番でなければ、この時点で例外になる。実 API の応答では観測していないため、実データで
例外になることは想定していない。
