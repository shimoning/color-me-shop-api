# ADR 0035: 公式 API にない機能をライブラリで作らない

- 状態: 採用
- 決定日: 2026-10-07

## 文脈

[ADR 0033](0033-unify-client-and-service-method-names.md) で、`Client` のページングする一覧取得を
`get<対象>Page()` に改名した。その際、旧名の `getProducts()` などは、ページを順にたどる全件取得を実装する
ときに全件を返すメソッドとして使う予定とし、README の「0.25.0 の変更」と 0.25.0 のリリースノートにも書いた。

2026-10-07 に公式 OpenAPI（`https://api.shop-pro.jp/v1/spec/open_api.json`）を確かめたところ、ページングする
6 つの API に、全件を 1 回で返すパラメータやエンドポイントはなかった。どれも `limit` と `offset` でページを
たどる形で、`limit` には上限がある。

| API | `limit` の既定値 | `limit` の上限 |
| --- | ---: | ---: |
| `GET /v1/products` | 10 | 50 |
| `GET /v1/stocks` | 10 | 50 |
| `GET /v1/products/{product_id}/variants` | 10 | 50 |
| `GET /v1/sales` | 10 | 100 |
| `GET /v1/customers` | 10 | 100 |
| `GET /v1/product_advertisings` | 50 | 250 |

同日に実 API で確かめたところ、既定値はすべて公式 OpenAPI のとおりで、上限を超える `limit` はエラーにならず
上限に丸められた（`meta.limit` の値で判断した。観測したショップの件数が少なく、上限の件数まで要素が返るかは
確かめていない）。ただしバリエーション一覧の上限は、公式 OpenAPI の 50 ではなく 100 だった。詳細は[ページングの limit の実測記録](../api-pagination-limit-observation.md)
にある。出典: `7688418`。

全件取得をライブラリで作るには、`offset` を進めながら繰り返し呼び出す必要がある。公式 OpenAPI は、
アクセストークンごとに 1 分あたり 120 リクエストを目安とし、超えたリクエストを 429 で拒否するとしている。
繰り返しの呼び出しでは、429 の再試行、途中のエラーの扱い、件数が多いときのメモリの扱いを、ライブラリが
決めることになる。

## 判断

- **公式 API にない機能は、ライブラリで作らない。** ライブラリは公式 API に準拠し、ページをたどる全件取得の
  ように、複数のリクエストを組み合わせて公式 API にない結果を作る機能は提供しない。利用者の指示
  「全件取得のAPIがないものは対応しない。あくまでAPIに準拠する。」（2026-10-07）による。この指示を受けて
  全件取得の予定を取り消した変更の出典: `57f9c34`。
- **ADR 0033 の「ページングの旧名を、全件取得を実装するときに全件を返すメソッドとして使う」予定を取り消す。**
  `getProducts()` などの旧名は、意味を変えずに非推奨のまま残し、次のメジャーな変更で削除する。出典: `57f9c34`。
- 全件を返す一覧取得（`get<対象の複数形>()`）は、API が全件を返すもの（`getPayments()` など）に限る。
  出典: `57f9c34`。

## 代替案と却下理由

- **ページを順にたどる全件取得を `get<対象の複数形>()` として作る案**は、利用者が繰り返しの処理を書かずに
  済む。しかし公式 API にない振る舞いで、レート制限・途中のエラー・メモリの扱いをライブラリが決めることに
  なる。利用者の指定により、作らない。

## 帰結

ライブラリが、公式 API の仕様にない振る舞いを持たない。

次の点が変わる。

- ページングする API の全件が必要な利用者は、`get<対象>Page()` を `offset` を進めながら呼び出す処理を自分で
  書く必要がある。レート制限への対応も利用者が行う
- 0.25.0 で予告した、ページングの旧名の意味の切り替え（`Page` から全件への戻り値の変更）は行わない。
  旧名は非推奨のまま削除される
