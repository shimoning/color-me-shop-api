# ADR 0039: 商品一覧の sort のカラム名を公式 OpenAPI の 5 つに限る

- 状態: 採用
- 決定日: 2026-10-08

## 文脈

[ADR 0038](0038-represent-sort-with-value-object.md) で、商品一覧の検索条件の `sort` を文字列の配列で受け、各要素を
汎用の値オブジェクト `Values\Sort` にした。`Values\Sort` はカラム名の形式だけを検証し、カラム名そのものは検証して
いなかった。

2026-10-08 に実 API で確かめたところ、商品一覧の並び順に使われたのは、公式 OpenAPI が挙げる 5 つのカラム
（`make_date`、`update_date`、`sales_price`、`price`、`members_price`）だけだった。商品が持つほかの 44 個のキー、
大文字・小文字を変えた名前、でたらめな値は、いずれもエラーにならず、並び順に使われなかった。詳細は
[商品一覧の sort の実測記録](../api-product-sort-observation.md)にある。出典: `c105183`、`e137d3c`。

そのため、仕様にないカラム名を指定しても、利用者はエラーで気づけず、意図しない既定の並びを受け取っていた。

## 判断

- **商品一覧の `sort` のカラム名を、公式 OpenAPI の 5 つに限る。** 大文字・小文字を区別して完全一致で確かめ、
  それ以外は送信前に拒否する。利用者の指定による。出典: `3bfbc5d`。
- **`Values\Limit` と同じ形で、汎用の `Values\Sort` を継承する商品専用の `Values\Product\Sort` を作る。**
  `Values\Sort` に、受け付けるカラム名の一覧を表す定数 `FIELDS` を加え、子クラスで上書きする。既定は制限なしで、
  汎用の `Values\Sort` の挙動は変えない。利用者の指定による。出典: `3bfbc5d`。
- 商品の検索条件の `sort` の各要素は `Values\Product\Sort` にする。受け付ける形（文字列の配列）と送信形式は
  ADR 0038 のまま変えない。出典: `3bfbc5d`。

## 代替案と却下理由

- **カラム名を検証しないままにする案**（ADR 0038 の判断）は、API がカラムを増やしてもライブラリの変更が要らない。
  しかし実測で、仕様にないカラム名は黙って無視され、利用者が誤りに気づけないことが分かった。
- **カラム名を enum で表す案**は、型でカラムを限れる。しかし ADR 0038 で、カラム名は文字列で受けると決めており、
  値オブジェクトの中で一覧と照らし合わせる形で足りる。
- **商品の検索条件で `Values\Sort` のまま、検索条件の側でカラム名を確かめる案**は、値オブジェクトを増やさずに済む。
  しかし API ごとの制約を値オブジェクトの子クラスで表す `Values\Limit` の形と揃わない。

## 帰結

商品一覧の `sort` に仕様にないカラム名を渡すと、送信前に誤りが分かる。

次の点が変わる。

- 商品の検索条件の `sort` に、5 つ以外のカラム名（大文字・小文字の違いを含む）を渡すと、生成時に
  `InvalidFieldException` になる。これまでは送信され、実 API が無視していた
- 商品の検索条件の `toArray()` の `sort` の要素は、`Values\Product\Sort`（`Values\Sort` の子クラス）になる
- 公式 OpenAPI のカラムが増えた場合は、`Values\Product\Sort` の一覧を更新する必要がある
- 受け付けるカラムは 1 ショップでの観測と公式 OpenAPI による
