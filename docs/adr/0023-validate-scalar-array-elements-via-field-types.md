# ADR 0023: スカラー配列の要素型を FIELD_TYPES で宣言して検証する

- 状態: 採用
- 決定日: 2026-10-01

## 文脈

Entity の配列プロパティのうち、`list<int>` や `list<string>` と宣言したスカラー配列は、要素の型が
実行時に検証されるかどうかがフィールドによって異なっていた。

基底 `Entity` が値の変換を行うのは、`OBJECT_FIELDS`（本 ADR で `FIELD_TYPES` に改名）に登録された
フィールドだけである。登録できるのは子 Entity・enum・値オブジェクトとその配列で、スカラー配列は
登録できなかった。登録のないフィールドについて基底 `Entity` が確かめるのは、外側が配列であることだけ
である。そのため要素の型を守るには、各 Entity のコンストラクタで個別に検証するしかなかった。

[ADR 0018](0018-unify-array-annotations-without-list-validation.md) はこの状態を限界として記録していた。

> 素の `array` プロパティでは、要素の型もキーの連番性も実行時には検証されない。（中略）`list<…>` の
> 宣言は、公式 API 契約と実測に基づく応答の形を述べたものであり、利用者が手で組み立てた配列に対する
> 保証ではない。

実際には、個別の検証を書いたフィールドと書いていないフィールドが混在していた（Issue #88）。

| | 要素を検証していた | 要素を検証していなかった |
| --- | --- | --- |
| 応答側 | `Product` の `group_ids` / `unavailable_payment_ids` / `unavailable_delivery_ids`、`Advertising` の `colors` / `sizes`、`Option` の `values`、`DeliveryDateTimes` の `periods` | `Delivery` の `unavailable_payment_ids`、`SaleDelivery` の `detail_ids`、`SaleSegment` の `siblings_sale_ids` |
| 要求側 | `Product` / `Advertising` / `Stock` の検索条件、`ProductInput` | `Sales` の検索条件の `ids` / `customer_ids` / `payment_ids` / `fields`、`Customer` の検索条件の `ids`、`SaleDelivery` を継承する `SaleDeliveryUpdateInput` の `detail_ids` |

**同じ API フィールド `unavailable_payment_ids` でも、`Product` は不正な要素を `InvalidFieldException`
にし、`Delivery` は何でも受け付けていた。** 利用者は、どちらを前提にすべきか判断できなかった。PHPStan
は `list<int>` の宣言を信頼するため、宣言と異なる値が入っても利用者側の静的解析では検出できない。

2026-10-01 に実データの要素の型を観測した。詳細は
[配列フィールドの JSON 形状の実測記録](../api-array-shape-observation.md)にある。出典: `e03f362`。

- 観測できた要素はすべて `int` で、公式 OpenAPI の `array` of `integer` と一致した
- `Delivery` の `unavailable_payment_ids` は空配列しか観測できず、`siblings_sale_ids` は未観測だった

いずれのフィールドでも、仕様と異なる値は観測していない。本件は、仕様変更や障害のときにだけ起こりうる
防御的な課題である。

## 判断

- **`OBJECT_FIELDS` を `FIELD_TYPES` に改名する。** 変換だけでなく要素型の検証も宣言するようになり、
  「オブジェクトに変換するフィールド」という名前が実態に合わなくなるためである。既存の `FIELD_NAMES`
  （API フィールド名の対応表）と対になる名前にする。旧名の互換は残さない。出典: `25ce907`。
- **`FIELD_TYPES` にスカラー配列の宣言 `['array' => true, 'scalar' => 'int'|'string']` を加え、基底
  `Entity` で要素の型を検証する。** 各 Entity のコンストラクタに個別の検証を書く方式をやめ、宣言に
  寄せる。不正な要素は `InvalidFieldException::forArrayElement()` にする。出典: `fef6853`。
- 要素の判定は厳密に行う（`int` は `is_int`、`string` は `is_string`）。数字の文字列を `int` に変換する
  などの変換はしない。既存の個別実装と同じ判定である。出典: `fef6853`。
- キーの連番性は検証も正規化もしない。ADR 0018 の判断を保つ。出典: `fef6853`。
- 外側が配列でない値は、要素の検証をせず、従来どおり外側の型の検証に任せる。出典: `fef6853`。
- 既存の個別実装のうち、単純な型の判定だけのものは宣言へ移す。不正なフィールドが 1 つだけの入力に
  ついて、例外クラスとメッセージは変えない。`ProductInput::$groupIds` はリスト形状の検証を伴うため、
  個別実装のまま残す。出典: `fef6853`。
- 要素を検証していなかった 8 フィールド（表の右列）に宣言を加える。根拠は応答側と要求側で異なる。
  応答側の 3 フィールドは公式 OpenAPI の `array` of `integer` に加え、実データを観測した。要素を
  確かめられたのは `SaleDelivery` の `detail_ids` だけ（すべて `int`）で、`Delivery` の
  `unavailable_payment_ids` は空配列のみ、`SaleSegment` の `siblings_sale_ids` は未観測である。
  出典: `e03f362`、`fef6853`。
- 要求側の 5 フィールド（`Sales` / `Customer` の検索条件）は利用者が組み立てる入力であり、実データの
  観測対象ではない。公式 OpenAPI の型と既存の PHPDoc の宣言（`fields` は `list<string>`、ほかは
  `list<int>`）に合わせ、すでに要素を検証している `Product` / `Stock` の検索条件と揃える。出典: `fef6853`。
- `list<int>` / `list<string>` のプロパティに宣言の漏れがないことを、横断テストで確かめる。宣言の
  代わりに個別実装を残すものは、理由付きの例外一覧に登録する。出典: `fef6853`。

ADR 0018 の「素の `array` プロパティでは、要素の型も実行時には検証されない」という記述のうち、
スカラー配列の要素の型については本 ADR で更新する。キーの連番性を検証しない判断はそのまま残る。

## 代替案と却下理由

- **未検証の各 Entity のコンストラクタに、既存と同じ個別の検証を足す案**は、変更が最小で、既存の
  動いているコードに触れない。しかし同じ形の検証が 10 か所以上に散らばったままになり、新しい配列
  フィールドを足したときに書き忘れる構造が残る。今回の不揃いはまさにその書き忘れから生じたため、
  利用者と協議のうえ採用しない。
- **個別の検証を足し、漏れは横断テストだけで防ぐ案**は、既存のコードに触れずに今後の漏れを防げる。
  しかし検証の実装そのものは各所に残り、メッセージや判定の揃い方はテストでしか保証されない。宣言に
  寄せれば判定とメッセージが 1 か所にまとまるため、利用者と協議のうえ採用しない。
- **数字の文字列を `int` に変換して受け付ける案**は、応答側で Entity の構築が失敗しにくくなる。しかし
  既存の個別実装はいずれも厳密な判定であり、ここだけ緩めると同じフィールドで挙動が揃わない。実データ
  では `int` 以外を観測していないため、変換の必要もない。
- **不正な要素を拒否せず `array_values()` などで正規化したり、要素を捨てたりする案**は、構築が失敗
  しない。しかし ADR 0018 がキーの正規化を採らなかったのと同じく、どの値をどう直すかを基底 `Entity` が
  知る必要がある。不正な値を黙って捨てると、利用者が仕様と異なる応答に気づけない。
- **`OBJECT_FIELDS` の名前を残し、スカラー配列の宣言だけを加える案**は、改名による影響がない。しかし
  「オブジェクトに変換する」という名前の宣言に、変換を伴わない要素型の検証が入ることになり、名前と
  実態のずれが大きくなる。利用者と協議のうえ採用しない。
- **旧名 `OBJECT_FIELDS` を非推奨として残し、基底 `Entity` が両方を読む案**は、`Entity` を継承した
  利用者のクラスを壊さない。しかしこのライブラリの拡張点は `ClientInterface` の注入であり、`Entity` の
  継承ではない（[ADR 0001](0001-testing-boundaries-and-http-client-injection.md)、
  [ADR 0020](0020-accept-state-in-authorization-url.md)）。両方を読む分岐と、両方を定義したときの優先
  順位を持ち込む必要もあるため、利用者と協議のうえ採用しない。

## 帰結

スカラー配列の要素の型が、すべてのフィールドで同じ規則で検証される。同じ API フィールドで、Entity に
よって挙動が違うことはなくなる。検証は `FIELD_TYPES` の宣言 1 行で足せるようになり、漏れは横断テストで
検出される。

次の挙動が変わる。破壊的変更のため、次のマイナーバージョン（0.21.0）で行う。

- 上記 8 フィールドに `int` 以外（`fields` は `string` 以外）の要素が含まれると、`InvalidFieldException`
  になる。応答側では Entity の構築が失敗し、要求側では検索条件や入力の生成時に失敗する。実データでは
  仕様どおりの値しか観測していない
- `Entity` を継承して `OBJECT_FIELDS` を定義していた場合、その定義は読まれなくなる。`FIELD_TYPES` に
  改名する必要がある
- 宣言へ移した既存のフィールドでも、次の 2 点は変わる。いずれも単独の不正値については従来と同じ
  例外とメッセージになる
  - **不正なフィールドが複数あるとき、最初に報告されるフィールド。** 従来の個別実装はコンストラクタの
    冒頭でスカラー配列を先に検証していたため、入力の順序によらず配列要素の誤りが先に報告された。
    共通処理は入力の順に検証するため、たとえば `Product` に `account_id` の型の誤りと `group_ids` の
    要素の誤りが両方ある場合、入力で先に現れたほうが報告される
  - **サブクラスでのメッセージのクラス名。** 従来の個別実装は宣言したクラス（`self::class`）を、共通処理は
    実際のクラス（`static::class`）をメッセージに入れる。利用者が `Product` などを継承していた場合、
    メッセージにはサブクラス名が入る。`Entity` の継承は互換性の契約の外にあるため、許容する。継承を
    使うライブラリ内の `SaleDeliveryUpdateInput` では、実際のクラス名が入るほうが正確である。出典: `fef6853`

例外の生成箇所が基底 `Entity` の共通処理に集約されたため、生成箇所ごとにメッセージを検証する契約
テストでは、生成箇所の登録を 1 件に保ち、各経路のメッセージは追加の契約として検証する。

採用済みの ADR や観測記録の中の `OBJECT_FIELDS` という表記は、当時の名前として書き換えない。
