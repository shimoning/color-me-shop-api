# ADR 0017: 応答に使う値オブジェクトへ opt-in のフォールバックを導入する

- 状態: 採用
- 決定日: 2026-09-25

## 文脈

`Entity` は `OBJECT_FIELDS` の `value` 指定を見て、応答のフィールドを `Values\Value` の実装へ変換する。
変換は常に値オブジェクトのコンストラクタを通るため、コンストラクタが検証に失敗して
`ParameterException` を投げると、そのフィールドを持つ Entity 全体が構築できない。出典: `d1960c1`。

2026-09-25 にテスト用ショップで、管理画面から顧客のフリガナに `ヷヸヹヺ` を入力して保存した。
API の応答では、この値が HTML 数値文字参照をデコードしないリテラル文字列として返った。
先頭のカタカナに続けて `&#12535;` `&#12536;` `&#12537;` `&#12538;` が並ぶ形であり、
`html_entity_decode()` すると入力した文字に戻る。

`Values\Furigana` の許容文字は `^[ァ-ヶー 　]*$` であり、`&`・`#`・数字・`;` を含まない。このため
`Services\Customer::one()` はこの顧客を取得できず `InvalidFieldException` になった。同じ顧客を含む
ページでは `Services\Customer::page()` も失敗し、**一覧全体が取得不能**だった。

この不具合は 0.14.0 で導入したものではない。0.13.0 以前のパターン `^[ァ-ヶー 　]+$` でも数値文字参照は
拒否されるため、元から存在していた。

同じ値を API 経由で書き込もうとすると `422`（code `422003`、`field: customer.furigana`、
「フリガナを正しく入力してください。」）で拒否された。この値は API 経由では書き込めず、管理画面
からのみ入る。

[ADR 0015](0015-model-customer-write-api.md) は帰結として、`ヷヸヹヺ` を含むフリガナが応答に現れれば
`ParameterException` になること、実 API が保存できない以上は現れないと考えられるが管理画面など
API 以外の経路で設定された値は未検証であることを記した。今回の観測はその未検証の場合に当たり、
実際に応答へ現れて Entity の構築を失敗させることが分かった。

[ADR 0009](0009-opt-in-enum-fallback.md) は、`Customer.external_accounts[].provider` で同じ構図の
問題に対処している。API 側に新しい値が増えると、既知の値でない応答のせいで Entity 全体を構築
できなくなる前方互換性のリスクがあるため、未知の backing value を専用 case へ変換する
`Constants\FallbackEnum` を opt-in で導入した。[ADR 0013](0013-expand-opt-in-enum-fallback.md) は
その対象を広げつつ、要求側では番兵値と未知値を厳格に拒否する契約を定めている。

値オブジェクトには、これに相当する仕組みがなかった。

## 判断

- `Values\FallbackValue` を導入する。`Values\Value` を継承し、検証に通らない生の値から
  インスタンスを作る手段と、保持している値が API 仕様どおりかを判定する手段を持つ。
- `Entity` が `OBJECT_FIELDS` の `value` を構築する際、対象が `FallbackValue` を実装しており、かつ
  コンストラクタが検証失敗で例外を投げた場合に限り、**応答文脈でのみ**生の値を保持した
  インスタンスへフォールバックする。
- 要求文脈では従来どおり例外を投げる。文脈の判定には、`buildEnum()` が enum のフォールバックで
  使っているものと同じ `$this instanceof RequestEntity || self::$_requestContext` を用いる。
  要求側を厳格に保つ [ADR 0013](0013-expand-opt-in-enum-fallback.md) の契約を維持する判断である。
- フォールバックは `FallbackValue` を実装したクラスにだけ適用する opt-in とする。`Values\DateTime` や
  `Values\Limit` など他の値オブジェクトの挙動は変えない。ADR 0009 の enum と同じ方針である。
- `Values\Furigana` に `FallbackValue` を実装する。応答で検証に通らない値が来ても、生の文字列を
  保持したまま Entity を構築できるようにする。
- フォールバックした値をライブラリ側でデコードや正規化はしない。`get()` は API が返した文字列を
  そのまま返し、値が API 仕様どおりかは利用者が判定できるようにする。数値文字参照を文字へ戻すかは
  利用者の判断に委ねる。
- 実測したエラーコード `422003` を `Constants\ErrorCode` に追加する。

## 代替案と却下理由

- `Entities\Customer\Customer` の `furigana` を値オブジェクトではなく素の `string` として保持する案は、
  最も単純で、検証に失敗する余地がなくなる。しかし `getFurigana()` の戻り値型が変わる破壊的変更で
  あり、値オブジェクトによる表現を失う。同じ問題は他の値オブジェクトでも起こりうるため、個別の
  フィールドを `string` へ戻す対処は再発を防げない。採用しない。
- `Values\Furigana` が構築時に `html_entity_decode()` して受け入れる案は、管理画面で入力された本来の
  値を表現できる。しかし API が返した値をライブラリが書き換えることになり、利用者が生の応答と
  突き合わせられなくなる。また、デコード後の `ヷヸヹヺ` は実 API が書き込みを拒否する文字であり、
  応答側の許容範囲を要求側と食い違わせる判断が別途必要になる。数値文字参照以外の未知の値にも
  対処できない。採用しない。
- `Values\Furigana` の許容文字集合を広げて数値文字参照の形を含める案は、今回観測した値だけは
  通せる。しかし管理画面が他の文字をどう変換するかは未観測であり、その都度パターンを広げることに
  なる。値オブジェクトの検証が意味を失うため採用しない。
- 応答側では値オブジェクトの検証を一律に無効化する案は、あらゆる未知の値を通せる。しかし
  `Values\DateTime` のように検証が利用者の役に立っている値オブジェクトまで緩めることになり、
  ADR 0009 が enum で opt-in を選んだ判断とも一致しないため採用しない。

## 帰結

管理画面など API 以外の経路で設定された値が応答に現れても、Entity 全体の構築は失敗しなくなる。
該当する顧客を含む一覧も取得できる。

利用者は、値オブジェクトが常に API 仕様どおりの値を保持するとは限らなくなる。`FallbackValue` を
実装した値オブジェクトについては、値の妥当性を判定してから使う必要がある。

要求側の厳格さは変わらない。検証に通らない値を要求へ載せようとすると従来どおり例外になる。

フォールバックの適用は `FallbackValue` を実装したクラスに限られるため、他の値オブジェクトで同じ
問題が起きた場合は、その都度インターフェースを実装するかどうかを判断する。
