# ADR 0036: 一覧取得の limit を API ごとの上限で検証する

- 状態: 採用
- 決定日: 2026-10-07

## 文脈

ページングする一覧取得の検索条件の `limit` は、扱いが揃っていなかった。

- 受注・顧客・在庫の検索条件は `Values\Limit` で検証し、1 〜 100 を受け付けていた
- 商品・バリエーション・商品広告の検索条件は `int` のままで、検証していなかった

2026-10-07 に実 API で確かめたところ、`limit` の上限は API ごとに違い、上限を超える値はエラーにならず上限に
丸められた。`limit=0` と `limit=-1` もエラーにならず、要素は返らなかった。詳細は
[ページングの limit の実測記録](../api-pagination-limit-observation.md)にある。出典: `7688418`、`e434e26`、`438fe99`。

| API | 上限（`meta.limit`） |
| --- | ---: |
| `GET /v1/products` | 50 |
| `GET /v1/stocks` | 50 |
| `GET /v1/products/{product_id}/variants` | 100（公式 OpenAPI は 50） |
| `GET /v1/sales` | 100 |
| `GET /v1/customers` | 100 |
| `GET /v1/product_advertisings` | 250 |

その結果、ライブラリと API の間に次のずれがあった。

- 在庫では、ライブラリが受け付ける 51 〜 100 を、API が 50 に丸めていた。利用者は指定した件数が返ると思い込む
- 商品・バリエーション・商品広告では、0 以下も上限を超える値もそのまま送っていた
- `Values\Limit` は上限が 100 に固定されており、API ごとの上限の違いを表せなかった

## 判断

- **一覧取得の検索条件の `limit` は、すべて値オブジェクトで検証する。** 上限は API ごとに実 API で確かめた値と
  し、下限は 1 とする。範囲外の値は、検索条件の生成時に `InvalidFieldException` で拒否する。出典: `fb563a5`。
- 上限は公式 OpenAPI の記述ではなく、実 API で確かめた値に合わせる。バリエーション一覧は、公式 OpenAPI が 50 と
  説明しているが、実 API が受け付ける 100 を上限とする。出典: `fb563a5`。
- `limit=0` は受け付けない。実 API は受け付けて `meta.total` だけを返すが、顧客一覧の公式 OpenAPI は最小値を 1 と
  しており、利用者の指定により 1 以上とする。出典: `fb563a5`。
- **`Values\Limit` を基底クラスにし、上限だけを上書きした API ごとの子クラスを作る。** 子クラスは API の URL に
  沿った名前空間（ADR 0030 の規則）に置く。出典: `fb563a5`。
  - `Values\Product\Limit`（50）、`Values\Product\Stock\Limit`（50）、`Values\Product\Variant\Limit`（100）、
    `Values\Product\Advertising\Limit`（250）、`Values\Sale\Limit`（100）、`Values\Customer\Limit`（100）
- `Values\Limit` を単体で使ったときの範囲（1 〜 100）は変えない。出典: `fb563a5`。
- `limit` は、ほかの値オブジェクトのフィールドと同じく整数で指定し、値オブジェクトのインスタンスは受け付けない。
  出典: `fb563a5`。

## 代替案と却下理由

- **検証しない案**は、API の挙動にそのまま従う。`limit=0` で件数だけを取る使い方もできる。しかし上限を超える値を
  黙って丸められ、利用者は指定した件数が返らないことに気づけない。
- **公式 OpenAPI の上限で検証する案**は、仕様どおりになる。しかしバリエーション一覧で、実 API が受け付ける
  51 〜 100 を拒否してしまう。
- **`Values\Limit` のコンストラクタに上限を渡す案**（`new Limit(30, max: 50)`）は、クラスを増やさずに済む。しかし
  検索条件の `FIELD_TYPES` は値を 1 つしか渡せず、Entity の基底クラスに引数を渡す仕組みを足す必要がある。
- **`FIELD_TYPES` に上限を書き、Entity の基底クラスで検証する案**は、値オブジェクトを増やさずに済む。しかし
  `limit` を値オブジェクトで検証するという利用者の指定から外れる。

## 帰結

`limit` の範囲が、検索条件ごとの値オブジェクトのクラスで表され、実 API の上限と揃う。

次の点が変わる。破壊的変更のため、次のマイナーバージョンで行う。

- これまで送れていた次の値が、検索条件の生成時に `InvalidFieldException` になる
  - 在庫の 51 〜 100、商品の 51 以上、バリエーションの 101 以上、商品広告の 251 以上。API 側では上限に丸められた
  - 商品・バリエーション・商品広告の 0 以下。観測した `0` と `-1` は、API 側で要素が返らなかった。`-2` 以下の
    API の挙動は確かめていないが、ライブラリでは拒否する
- 商品・バリエーション・商品広告の検索条件の `limit` のプロパティが、`int` から値オブジェクトになる。`toArray()`
  の `limit` は値オブジェクトになる。送信するクエリ（`toArrayRecursive()`）は従来どおり整数である
- `Values\Limit` の上限を超えたときの例外メッセージは、子クラスの上限を含む

上限は 1 ショップでの観測による。観測したショップの件数が少なく、上限の件数まで実際に要素が返るかは確かめて
いない。
